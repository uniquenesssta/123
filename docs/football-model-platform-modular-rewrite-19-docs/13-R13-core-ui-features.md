# R13：基础数据与编排类 UI Feature 完整重写——独立执行任务书

> 文档编号：`R13`  
> 前置阶段：`R12`  
> 后续阶段：`R14`  
> 本文档是唯一执行依据之一；必须与 `00-总体架构与前23节.md` 同时适用。

## 1. 阶段目标

- 按 Feature 垂直切分 Dashboard、Database、Competitions、Rules、Teams、Players、Lineup Presets、Lineups、Workbooks、Architecture。
- 删除这些领域在旧 main/API/pages/CSS 中的全部实现。

## 2. 本阶段解决的实际问题

- 旧页面状态、API、Controller、View 和 CSS 跨文件混杂，后续新想法难以确定归属。

## 3. 前置输入与进入条件

- R12 Foundation 全部通过。
- 对应后端命令和契约稳定。

## 4. 明确范围

### 4.1 纳入范围

- 10 个基础数据与编排 Feature 的 module/page/state/api/mapping/policies/workflows/views/styles/tests。

### 4.2 排除范围

- Prediction/Review/Analytics/AI 高风险 UI。

## 5. 当前实现来源与扫描重点

- `src/main.ts` 中各 Feature 状态和动作。
- `src/api/client.ts` 对应命令。
- `src/pages/`、`src/components/`、`src/controllers/` 和旧 CSS。

## 6. 目标目录总览

```text
src/features/dashboard/
src/features/database/
src/features/competitions/
src/features/rules/
src/features/teams/
src/features/players/
src/features/lineup-presets/
src/features/lineups/
src/features/workbooks/
src/features/architecture/
```

## 7. 目录与文件边界规则

- 每个 Feature 固定拥有 module/page/state/api/mapping/policies/workflows/views/styles/tests。
- 一个 API 命令一个文件。
- 复杂子模块必须是目录，不能重新合并成页面文件。

## 8. 数据流、调用流与依赖方向

```text
route -> feature module -> page controller -> feature state/selectors -> views
user action -> controller/workflow -> feature api -> Tauri transport -> state update
```

## 9. 状态所有权与事务边界

- 每个 Feature 根 State 唯一拥有该业务页面状态。
- 多步骤导入、删除、阵容提交由独立 Workflow State 拥有。

## 10. 公共契约与兼容要求

- 搜索、分页、选择、详情、编辑、删除、导入、工作区恢复和路由上下文行为保持。

## 11. 风险与禁止事项

- 不得把多个子模块重新放入 `teamPage.ts` 或 `playerPage.ts`。
- 不得在 Feature 间直接导入内部文件。

## 全阶段强制执行规则

1. 本阶段只允许修改本阶段明确列出的目标模块，不得夹带无关重命名、格式化、依赖升级或功能变化。
2. 模型保护区 `crates/model-api/`、`crates/model-p4/`、`crates/model-p7/` 以及关联参数、Profile、Schema、fixture、Golden Master 不得修改。
3. 任何原文件出现第二个独立职责时，必须把该职责模块升级为目录：原职责迁入具名文件，新职责进入新的具名文件；不得继续向原文件追加。
4. 不得使用 `old`、`new`、`legacy`、`copy`、`final`、`v2` 作为长期文件名或目录名。所谓旧职责和新职责必须使用真实业务语义命名。
5. 每条公共 Tauri 命令、DTO 字段、数据库格式、配置键、错误语义、日志等级和用户可观察行为默认保持兼容。
6. 每个业务状态只能有一个所有者；View 不拥有业务状态，API 不拥有页面状态，Repository 不拥有工作流状态。
7. 新旧实现只能在单个 Atomic Task 的受控切换窗口内短暂共存；任务结束前必须切换唯一入口并删除旧实现。
8. 不得新增生产依赖。确有必要时，必须单独提交依赖评估，不得混入业务任务。
9. 每个 Atomic Task 必须先通过最小验证，再运行阶段回归；硬性验证失败立即停止，不得进入下一任务。
10. 实际源码、配置、接口或行为发生变化时，同步更新根目录 `README.md`，只记录实际完成和实际验证结果。
11. 每个节点完成时必须创建 `docs/modular-rewrite/R13-core-ui-features/<task-record>.md` 并更新阶段 `README.md`；阶段完成时必须创建 `R13-stage-completion.md`。缺少记录不得标记为 `DONE`。

## 原计划阶段摘要（保留用于追溯）

## R13：基础数据与编排类 UI Feature 完整重写

每个 feature 必须执行统一的 14 步：

1. 冻结旧页面行为和命令清单；
2. 创建 `module/`、`page/`、`state/`、`api/`、`mapping/`、`policies/`；
3. 为每条命令创建一个 API 文件；
4. 创建 feature 根 state 和 selectors；
5. 按计划书创建全部子模块目录；
6. 子模块分别创建主协调、View、Controller、ViewModel；
7. 多步骤动作建立 `workflows/<name>/`；
8. 创建镜像 CSS 目录；
9. 创建镜像测试目录；
10. 完成 render、interaction、lifecycle、race、accessibility 测试；
11. 切换唯一路由入口；
12. 从旧 `main.ts` 和旧页面删除本域状态与动作；
13. 从旧 API client 删除本域命令；
14. 删除旧实现并运行阶段回归。

### R13-01 Dashboard

子模块：system-summary、database-health、recent-runs、attention-center、quick-actions。

### R13-02 Database

子模块：connection-status、connection-editor、migration-status、database-health、database-reset、database-statistics。

特别验证：密码/URL 脱敏、重置强确认、连接切换、迁移状态准确。

### R13-03 Competitions

子模块：competition-directory、competition-detail、season-management、stage-management、round-management、competition-routing。

特别验证：层级选择、编辑后保持上下文、删除/更新引用行为不变。

### R13-04 Rules

子模块：rule-package-directory、rule-package-editor、rule-package-validation、competition-binding、routing-preview。

特别验证：前端只做格式提示，正式规则合法性仍由后端决定。

### R13-05 Teams

子模块：team-directory、team-detail、team-identity、team-names、team-profile、team-roster、team-coaches、formation-usage、lineup-history、team-editor、team-delete、team-package。

每个子模块必须是目录，不允许重新合并成一个球队详情文件。

特别验证：

- 搜索、分页、选择独立；
- 详情和编辑状态独立；
- 删除预检与提交分离；
- 资料包 preview/commit 分离；
- 中文名、外文名和别名展示一致；
- 从球队跳转球员时只传稳定 ID。

### R13-06 Players

子模块：player-directory、player-detail、player-identity、player-names、player-positions、team-history、availability、abilities、dynamic-tags、match-history、player-editor、player-delete。

特别验证：

- 普通进入目录不会保留球队来源筛选；
- FIFA/内部位置映射由明确 Mapper 处理；
- 动态标签不覆盖能力观察；
- 效力区间、伤停和能力拥有独立编辑工作流。

### R13-07 Lineup Presets

子模块：preset-directory、preset-editor、preset-members、preset-preview、preset-duplicate、preset-archive。

特别验证：应用预设只产生预览结果，不直接写比赛阵容。

### R13-08 Lineups

子模块：match-directory、match-editor、paired-builder、lineup-side、player-selector、role-selector、formation-selector、builder-validation、lineup-history、lineup-import。

特别验证：主客双方同一状态所有者、原子提交、独立请求序号、失败不留下半条阵容。

### R13-09 Workbooks

子模块：player-catalog、team-package、monthly-team、monthly-player、match-lineup、match-review、workbook-preview、workbook-conflicts。

特别验证：每种工作簿独立 workflow state，真实 XLSX 预检、冲突和 commit，不使用 mock 替代。

### R13-10 Architecture Page

子模块：module-dependency、command-boundary、state-ownership、protected-model、file-responsibility。

只读展示，不能在 UI 修改架构清单或保护资产。

R13 阶段门禁：上述 feature 的旧页面、旧 API 方法、旧业务状态和旧 CSS 必须全部删除，不保留双实现。
