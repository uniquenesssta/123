# 1. 最终目标

根据实际业务、接口、数据库、工作流和模型调用链，形成可以长期扩展的模块化工程。复用已验证实现，按真实职责迁移集中点，并修复有证据的缺口。

最终必须达到：

- 路径能够表达模块归属；
- 文件名能够表达唯一职责；
- 一个文件只因一种原因变化；
- 一个状态只有一个所有者；
- 一个副作用只有一个执行入口；
- 一条用户动作可以从 UI 一直追踪到 application use case、port、adapter 和测试；
- 新想法不得迫使现有文件持续膨胀；
- 模型代码、模型参数和固定回归结果完全不变；
- 现有公共命令、数据、迁移、配置和用户可观察行为保持兼容。

“同一个页面”“同一个业务域”“同一个 crate”都不能作为把多种职责放进同一文件的理由。

# 2. 本次订正后的绝对规则

## 2.1 按职责决定文件与目录

新增独立业务能力、状态所有者、外部集成或不同依赖边界时，评估并建立清晰模块边界。职责内的私有校验、Row/Mapper 或事务步骤可以保留在同一文件；新增一个函数、测试或筛选项不自动触发目录升级。

## 2.2 拆分与迁移

已有文件仍承担同一职责时优先原位修改。确需拆分时，选择能清楚表达所有权的文件/目录布局，同步引用和调用方，保留唯一实现；不使用只转发的空壳伪装迁移完成，也不按行数平均切割。

## 2.3 “old/new”是职责关系，不是最终文件名

本任务书将用户所说的文件 old 和文件 new 理解为“原职责文件”和“新拆分文件”。最终不得出现 `old.ts`、`new.ts`、`v2.rs`、`final.ts` 等缺少业务语义的文件名。

## 2.4 整个项目统一执行

该规则覆盖：

- TypeScript；
- CSS；
- Rust；
- Tauri 命令；
- SQL 查询模块；
- 测试；
- 脚本；
- JSON 契约；
- 文档模块。

# 5. 全局依赖方向与组合根

```text
UI View
  ↓ events
UI Controller / Workflow
  ↓ commands
Feature State + Feature API
  ↓
Tauri Transport
  ↓
Tauri Command Adapter
  ↓
Application Use Case
  ↓
Domain + Ports
  ↓
Persistence / Research / Workbook / File adapters

Prediction Use Case
  ↓
model-api
  ↓
model-p4 / model-p7（保护区）
```

禁止反向依赖：

- Domain 不依赖 application、SQLx、Tauri、HTTP、XLSX；
- Application 不依赖具体 PostgreSQL、Tauri 或前端；
- Tauri command 不写 SQL、不实现业务规则；
- View 不调用 Tauri、不直接修改 store；
- Shared UI 不依赖 feature；
- Feature A 不导入 Feature B 内部文件；
- Persistence 不认识 UI DTO；
- 模型 crate 不认识数据库、文件或 UI。

系统只允许三个组合根：

- `src/bootstrap/createApplication.ts`；
- `src-tauri/src/bootstrap/create_app_state.rs`；
- `crates/application/src/composition/create_application.rs`。

# 10. UI 状态、事件、渲染与交互边界

## 10.1 单向流

```text
用户事件
→ Component/View 发出语义事件
→ Controller 解释动作
→ Workflow 或 State Action
→ Feature API
→ State 更新
→ Selector 生成 ViewModel
→ View 局部更新
```

禁止 View 直接调用 API，禁止 API 修改 DOM，禁止 Mapper 持有状态。

## 10.2 状态分类

| 状态类型 | 所有者 | 示例 |
|---|---|---|
| 全局会话状态 | `app/session` | 当前路由、主题、启动摘要 |
| 外壳状态 | `app/shell` | 侧栏展开、内容滚动位置 |
| Feature 根状态 | `features/<feature>/state` | 当前实体、加载状态、错误 |
| 子模块状态 | 对应子模块目录 | 筛选条件、分页游标、草稿 |
| 工作流状态 | `workflows/<workflow>` | 当前步骤、预检、确认、提交结果 |
| 组件内部状态 | 设计系统组件目录 | 展开、焦点、键盘索引 |
| 持久化 UI 状态 | 明确 snapshot 文件 | 可恢复标签页和筛选器 |

## 10.3 状态禁止项

- 不保存可从 DTO 派生的数据副本；
- 不让同一个实体同时存在于目录 state 和详情 state 的可变副本；
- 不把 API key、密码、prompt 正文写入可持久化 state；
- 不在全局 session 中保存业务表单；
- 不扫描 DOM 反向构建业务状态；
- 不用 `any` 绕过状态边界。

## 10.4 页面生命周期

每个页面必须具备：

```ts
mount(container, context): Promise<MountHandle>
```

`MountHandle.destroy()` 必须：

- 解绑全部事件；
- 取消或失效未完成请求；
- 销毁子模块；
- 释放定时器和 observer；
- 清理临时 DOM 引用；
- 不删除需要持久化的显式 state snapshot。

## 10.5 弹窗和警告

- 所有警告统一进入 `app/warning-center/`；
- 页面只提交结构化 warning，不自行堆积警告横条；
- 破坏性操作使用 `ui/patterns/destructive-action/`；
- 每个业务确认弹窗位于对应 workflow，不放入全局 dialog 文件；
- 弹窗关闭、Esc、遮罩点击和焦点恢复由设计系统 dialog 统一处理。

## 10.6 UI 可扩展性门禁

新增 UI 想法前必须回答：

- 它属于现有页面区域还是新页面；
- 是否拥有独立状态；
- 是否拥有独立事件；
- 是否拥有独立 API；
- 是否需要工作流目录；
- 是否需要新的设计系统原语；
- 是否会导致现有文件出现第二职责。

最后一项为“是”时，先明确新增职责的 owner 与依赖；按边界决定具名文件或子目录，不机械增加目录层级。

# 11. 前后端契约完整规划

```text
src/contracts/
├─ shared/
│  ├─ entityId.ts
│  ├─ timestamp.ts
│  ├─ pageCursor.ts
│  ├─ operationError.ts
│  └─ operationTrace.ts
└─ <feature>/
   ├─ index.ts
   ├─ common/
   │  └─ <stable-shared-feature-type>.ts
   └─ <command-name>/
      ├─ input.ts
      ├─ output.ts
      └─ error.ts                   # 只有命令存在专用错误时
```

规则：

- 一条 Tauri 命令对应一个契约目录；
- 输入、输出分文件，避免 DTO 文件无限增长；
- UI ViewModel 不进入 contracts；
- Domain entity 不直接作为 Tauri DTO；
- 公共基础类型只有在三个以上 feature 真正稳定共享时才进入 `shared/`；

# 20. 文件级强制规则

## 20.1 文件职责声明

每个非平凡文件顶部必须有简短模块注释，说明：

- 该文件负责什么；
- 该文件不负责什么；
- 主要输入输出。

不得写冗长过程说明。

## 20.2 文件规模审查

职责、状态所有权和依赖关系优先。TypeScript/JavaScript/CSS 250 行、Rust 300 行或 16KB、组合根 150 行为阅读与审查提示；超过 500 行或 24KB 应重点审查，但不因数字本身拒绝合并或强制拆分。

审查仅针对当前影响范围，说明是否存在独立变更原因、混合状态或跨层副作用。职责内聚的文件可以保留，将判断简记在节点记录即可；不强制为行数建立新的例外清单。保护资产、历史迁移、生成文件不得为压缩行数改写。

## 20.3 禁止文件名

禁止新建：

```text
utils.*
helpers.*
common.*
misc.*
manager.*
service.*   （除 application feature 的明确 service.rs）
new.*
old.*
legacy.*
copy.*
final.*
*v2.*
```

`service.rs` 只允许在应用服务边界中使用，且必须由目录名明确业务域。

## 20.4 Barrel 文件

`index.ts` / `mod.rs`：

- 只声明模块和导出。
- 不定义状态。
- 不执行副作用。
- 不写业务流程。

## 20.5 有依据的模块拆分

当文件承担独立状态、不同依赖/副作用或可独立演进的业务能力时，应为受影响职责建立明确 owner。可以在现有目录新增具名文件，也可以升级为子目录；不规定必须同名目录或每增加一项职责就递归加深层级。

分离 UI 状态、外部 I/O、业务规则和持久化等真实边界；紧密耦合、共同生命周期的私有实现可共置。不增加空 mod/index、重复配置、平行实现或无价值转发层。拆分后检查全部直接调用方、公共契约、依赖方向、状态归属和相关验证器。

## 20.6 单一状态所有者

每种状态必须在架构清单登记：

| 状态 | 唯一所有者 |
|---|---|
| 当前路由 | app/router |
| 主题 | app/themeState |
| 球队搜索和分页 | teams/teamQueryState |
| 球员搜索和分页 | players/playerQueryState |
| 配对阵容草稿 | lineups/lineupBuilderState |
| 推演上下文 | prediction/predictionContextState |
| 复盘步骤 | backend workflow + frontend reviewWorkflowState 投影 |
| AI 请求进行中状态 | aiWorkspace/requestState |
| 工作区面板和标签 | shared/workspace/workspaceState |
| 数据库连接 | backend Application database service |
| P4 冻结任务 | backend research domain/repository |
| 模型注册表 | application/model_registry |

任何新状态必须先明确所有者。

# 22. 新想法与未来功能的接入协议

任何未来新增想法都必须先完成模块归属，再进入编码；不得先把代码写进当前最接近的文件。

## 22.1 新需求进入前的八项定位

每个新想法必须明确：

1. 属于现有 feature、现有子模块，还是全新 feature；
2. 谁拥有它的业务状态；
3. 谁拥有它的副作用；
4. 是否新增公共契约；
5. 是否新增 Tauri 命令或 application use case；
6. 是否需要持久化、事务或迁移；
7. UI 中属于页面、区域、组件、弹窗还是工作流；
8. 需要哪些单元、契约、集成和 UI 回归测试。

其中任一项无法明确时，不得开始写代码。

## 22.2 新想法的目录决策树

```text
新想法
├─ 只改变现有单一职责内部实现
│  └─ 可修改原职责文件，但不得增加第二职责
├─ 为现有模块增加一个独立职责
│  └─ 按“文件升级为目录”规则创建子目录和新文件
├─ 为现有 feature 增加独立子功能
│  └─ 在 feature 下创建具名子模块目录
├─ 跨越两个 feature
│  ├─ 先判断是否是共享视觉原语
│  ├─ 先判断是否是应用级协调流程
│  └─ 禁止直接让两个 feature 共享可变状态
└─ 全新业务能力
   └─ 创建完整 feature + contract + use case + adapter + test 纵向切片
```

## 22.3 新 Feature 的能力链参考（按需要选用）

```text
src/features/<feature>/
contracts/<feature>/
crates/domain/src/<feature>/                 # 仅存在真正领域概念时
crates/application/src/features/<feature>/
crates/application/src/ports/<feature>/      # 仅存在外部端口时
crates/persistence-postgres/src/<feature>/   # 仅需要数据库时
src-tauri/src/commands/<feature>/
tests/contracts/<feature>/
tests/frontend/features/<feature>/
tests/integration/<feature>/
architecture/modules/<feature>.json
```

新增能力必须接通真实前后端链路；已有后端用例直接复用，不为了前端归属迁移再建同名后端层或迁移。上面的路径仅表达层次，具体采用仓库现有 owner，不强制建立所有目录。

## 22.4 模块清单同步

新增、删除、拆分或合并模块时，必须同步修改：

- `architecture/modules/<module>.json`；
- `architecture/module-boundaries.json`；
- `architecture/command-contract.json`（涉及命令时）；
- 对应契约、测试与 README 实施记录；
- 受影响目录的 `README.md`（仅顶级复杂模块需要）。

## 22.5 未来扩展的禁止路径

- 在 `main.ts` 增加页面业务；
- 在全局 API 客户端增加新命令；
- 在全局 `types.ts` 增加新 DTO；
- 在现有页面 view 中直接调用 API；
- 在 Tauri 命令中写 SQL；
- 在 application service 根文件追加业务流程；
- 在通用 CSS 文件追加 feature 样式；
- 通过复制旧模块创建 `xxx2`、`xxx_new`、`xxx_final`；
- 创建没有退出期限的兼容层。


# 23. 重写实施策略

## 23.1 分支

建议创建：

```text
rewrite/modular-platform
```

不使用 `new`、`final` 或版本后缀目录。

## 23.2 原子替换规则

每个 Atomic Task 必须遵循：

1. 明确旧实现所有文件。
2. 明确新模块目录和公共接口。
3. 增加或迁移测试。
4. 实现新代码。
5. 切换唯一调用入口。
6. 删除对应旧实现。
7. 运行最小验证。
8. 按本文件执行约束订正，使用现有入口完成与影响范围匹配的阶段回归。
9. 更新 README 实际变更。
10. 提交。

不允许：

- 新旧实现长期并存。
- 先复制旧文件再逐渐修改而没有删除时间。
- 用转发壳掩盖未完成迁移。
- 跨多个未验证业务域一次性替换。

## 23.3 阶段与节点实施记录制度

### 23.3.1 目的与效力

从 R0 开始，每完成一个阶段或一个阶段内的 Atomic Task，必须在仓库根目录 `docs/` 下保存对应的详细实施记录。该记录属于交付物和阶段门禁，不是可选说明。

规则效力：

- 源码已经实现但没有节点记录：任务不得标记为 `DONE`。
- 节点全部完成但没有阶段总结：阶段不得通过出口门禁。
- 只有根 `README.md` 摘要而没有 `docs/` 详细记录：视为记录不完整。
- 只有计划、预期或模板，没有填写真实变更与真实验证结果：视为未记录。
- 记录与 `git diff`、测试结果或最终代码不一致：阶段必须停止并订正。

根 `README.md` 继续承担项目级摘要；`docs/modular-rewrite/` 承担节点级和阶段级完整事实记录。两者不能互相替代。

### 23.3.2 固定目录


每个阶段目录至少包含：


- `README.md`：当前阶段索引、任务状态、记录链接、阶段门禁状态。

- `<stage-id>-stage-completion.md`：整个阶段完成后的汇总、阶段回归和进入下一阶段的依据。
- `evidence/`：保存需要长期保留且体积受控的验收证据，例如结构化报告、截图索引、迁移指纹摘要。不得提交构建产物、依赖缓存、数据库转储、密钥或巨量原始日志。

### 23.3.3 创建与更新时机

1. 阶段第一个任务进入 `READY` 前，创建阶段目录及其 `README.md`。
2. Atomic Task 进入 `IN_PROGRESS` 时，在阶段 `README.md` 中记录负责人、起始基线、影响范围和状态。
3. 完成代码、最小验证和阶段相关回归后，基于真实 `git diff` 创建该节点的详细记录。
4. 节点记录、根 `README.md` 摘要和阶段索引全部更新后，任务才可改为 `DONE`。
5. 阶段内所有节点完成并通过出口门禁后，创建 `<stage-id>-stage-completion.md`。
6. 阶段总结完成并与真实验证结果一致后，下一阶段第一个任务才可进入 `READY`。

不得在阶段末尾一次性凭记忆补写全部节点记录。记录必须随节点完成同步生成。
