# 足球赛事模型平台：模块化完全重写总纲（前 23 节）

> 本文件是 19 份执行文档中的第 1 份。  
> 它包含原计划前 23 节、执行前置 R0，以及所有阶段共享的 Atomic Task、提交、验收和首个 READY 规则。  
> 后续执行阶段分别位于 `01-R1` 至 `18-R18` 文档。

# 1. 最终目标

本次不是在旧结构上继续修补，也不是把旧大文件按行数平均切开，而是根据现有业务、接口、数据库、工作流和模型调用链，重新建立一套可以长期扩展的模块化工程。

最终必须达到：

- 路径能够表达模块归属；
- 文件名能够表达唯一职责；
- 一个文件只因一种原因变化；
- 一个状态只有一个所有者；
- 一个副作用只有一个执行入口；
- 一条用户动作可以从 UI 一直追踪到 application use case、port、adapter 和测试；
- 新想法不得迫使现有文件持续膨胀；
- 模型代码、模型参数和固定回归结果完全不变；
- 现有公共命令、数据、迁移、配置和用户可观察行为保持兼容。

“同一个页面”“同一个业务域”“同一个 crate”都不能作为把多种职责放进同一文件的理由。

# 2. 本次订正后的绝对规则

## 2.1 文件不是最终容器，模块目录才是最终容器

单文件只适用于真正不可再分的单一职责。只要它需要增加同模块的第二个职责，就必须创建同名或语义明确的目录，把原职责文件和新职责文件共同放入目录。

示例：

```text
原来：
features/teams/teamDirectory.ts

需要新增筛选后：
features/teams/team-directory/
├─ teamDirectory.ts
└─ teamFilters.ts
```

如果筛选继续变复杂，再递归创建 `team-filters/` 子目录，而不是回填 `teamFilters.ts`。

## 2.2 原文件可以移动，不能继续成为容器

- 原文件可以保留原名称并移动进新目录；
- 原文件只能继续承担原来的单一职责；
- 新职责必须有新文件；
- `index.ts` / `mod.rs` 只允许导出和最小组合；
- 不允许用转发壳伪装完成拆分。

## 2.3 “old/new”是职责关系，不是最终文件名

本任务书将用户所说的文件 old 和文件 new 理解为“原职责文件”和“新拆分文件”。最终不得出现 `old.ts`、`new.ts`、`v2.rs`、`final.ts` 等缺少业务语义的文件名。

## 2.4 整个项目统一执行

该规则覆盖：

- TypeScript；
- CSS；
- Rust；
- Tauri 命令；
- SQL 查询模块；
- 测试；
- 脚本；
- JSON 契约；
- 文档模块。

## 3.1 模型绝对保护区


# 4. 现有代码问题到目标结构的映射

| 现有集中点 | 当前风险 | 重写后的所有者 |
|---|---|---|
| `src/main.ts` | 启动、状态、渲染、事件、业务动作混合 | `bootstrap/`、`app/`、各 feature |
| `src/api/client.ts` | 所有命令、日志、文件、错误混合 | `platform/tauri/` + `features/*/api/` |
| `src/types.ts` | 全域 DTO 和 UI 类型混合 | `contracts/<feature>/` + feature view-model |
| 页面文件 | 页面全部功能、状态和 DOM 混合 | `page/`、`sections/`、`workflows/`、`state/` |
| 单一 feature CSS | 页面所有样式继续膨胀 | `styles/features/<feature>/<submodule>.css` |
| `domain/src/lib.rs` | 跨域实体集中 | `domain/src/<bounded-context>/` |
| application 大文件 | 查询、命令、校验、映射混合 | `use-cases/<action>/` 目录 |
| Tauri 大命令模块 | DTO、命令、映射和文件操作混合 | 一条命令一个目录或文件 |
| persistence repository | 多表、多查询、多事务混合 | `repositories/`、`queries/`、`transactions/` |
| scripts 根目录 | 验证职责平铺 | `scripts/<category>/<gate>/` |

# 5. 全局依赖方向与组合根

```text
UI View
  ↓ events
UI Controller / Workflow
  ↓ commands
Feature State + Feature API
  ↓
Tauri Transport
  ↓
Tauri Command Adapter
  ↓
Application Use Case
  ↓
Domain + Ports
  ↓
Persistence / Research / Workbook / File adapters

Prediction Use Case
  ↓
model-api
  ↓
model-p4 / model-p7（保护区）
```

禁止反向依赖：

- Domain 不依赖 application、SQLx、Tauri、HTTP、XLSX；
- Application 不依赖具体 PostgreSQL、Tauri 或前端；
- Tauri command 不写 SQL、不实现业务规则；
- View 不调用 Tauri、不直接修改 store；
- Shared UI 不依赖 feature；
- Feature A 不导入 Feature B 内部文件；
- Persistence 不认识 UI DTO；
- 模型 crate 不认识数据库、文件或 UI。

系统只允许三个组合根：

- `src/bootstrap/createApplication.ts`；
- `src-tauri/src/bootstrap/create_app_state.rs`；
- `crates/application/src/composition/create_application.rs`。

# 9. UI Feature 逐模块完整文件规划
## 9.1 每个 Feature 的固定骨架

每个 feature 必须先建立完整骨架，再按实际功能增加子模块：

```text
features/<feature>/
├─ index.ts                         # 唯一公共出口
├─ module/
│  ├─ <feature>Feature.ts           # 实现 FeatureModule
│  ├─ <feature>Route.ts             # 路由声明
│  └─ <feature>Navigation.ts        # 只定义本 feature 导航参数
├─ page/
│  ├─ <feature>Page.ts              # 页面挂载与销毁协调
│  ├─ <feature>PageView.ts          # 页面骨架 DOM
│  ├─ <feature>PageController.ts    # 页面级事件与子模块装配
│  └─ <feature>PageViewModel.ts     # 页面显示模型
├─ state/
│  ├─ <feature>State.ts             # 本 feature 根状态组合
│  ├─ <feature>Selectors.ts         # 派生状态
│  └─ <feature>StateSnapshot.ts     # 可恢复状态，若需要
├─ api/
│  ├─ index.ts                      # 只导出本 feature API
│  └─ <one-command-per-file>.ts     # 每条 Tauri 命令一个包装文件
├─ mapping/
│  └─ <specificMapper>.ts           # DTO 到 view model，不放业务规则
├─ policies/
│  └─ <specificPolicy>.ts           # 纯前端显示/交互策略
├─ workflows/
│  └─ <workflow-name>/              # 多步骤动作必须独立目录
└─ <submodule>/                     # 页面区域或业务子模块
```

禁止在 feature 根目录保留巨型 `<feature>Controller.ts`、`<feature>Api.ts`、`<feature>View.ts`。

# 10. UI 状态、事件、渲染与交互边界

## 10.1 单向流

```text
用户事件
→ Component/View 发出语义事件
→ Controller 解释动作
→ Workflow 或 State Action
→ Feature API
→ State 更新
→ Selector 生成 ViewModel
→ View 局部更新
```

禁止 View 直接调用 API，禁止 API 修改 DOM，禁止 Mapper 持有状态。

## 10.2 状态分类

| 状态类型 | 所有者 | 示例 |
|---|---|---|
| 全局会话状态 | `app/session` | 当前路由、主题、启动摘要 |
| 外壳状态 | `app/shell` | 侧栏展开、内容滚动位置 |
| Feature 根状态 | `features/<feature>/state` | 当前实体、加载状态、错误 |
| 子模块状态 | 对应子模块目录 | 筛选条件、分页游标、草稿 |
| 工作流状态 | `workflows/<workflow>` | 当前步骤、预检、确认、提交结果 |
| 组件内部状态 | 设计系统组件目录 | 展开、焦点、键盘索引 |
| 持久化 UI 状态 | 明确 snapshot 文件 | 可恢复标签页和筛选器 |

## 10.3 状态禁止项

- 不保存可从 DTO 派生的数据副本；
- 不让同一个实体同时存在于目录 state 和详情 state 的可变副本；
- 不把 API key、密码、prompt 正文写入可持久化 state；
- 不在全局 session 中保存业务表单；
- 不扫描 DOM 反向构建业务状态；
- 不用 `any` 绕过状态边界。

## 10.4 页面生命周期

每个页面必须具备：

```ts
mount(container, context): Promise<MountHandle>
```

`MountHandle.destroy()` 必须：

- 解绑全部事件；
- 取消或失效未完成请求；
- 销毁子模块；
- 释放定时器和 observer；
- 清理临时 DOM 引用；
- 不删除需要持久化的显式 state snapshot。

## 10.5 弹窗和警告

- 所有警告统一进入 `app/warning-center/`；
- 页面只提交结构化 warning，不自行堆积警告横条；
- 破坏性操作使用 `ui/patterns/destructive-action/`；
- 每个业务确认弹窗位于对应 workflow，不放入全局 dialog 文件；
- 弹窗关闭、Esc、遮罩点击和焦点恢复由设计系统 dialog 统一处理。

## 10.6 UI 可扩展性门禁

新增 UI 想法前必须回答：

- 它属于现有页面区域还是新页面；
- 是否拥有独立状态；
- 是否拥有独立事件；
- 是否拥有独立 API；
- 是否需要工作流目录；
- 是否需要新的设计系统原语；
- 是否会导致现有文件出现第二职责。

最后一项为“是”时，必须先升级目录再编码。

# 20. 文件级强制规则

## 20.1 文件职责声明

每个非平凡文件顶部必须有简短模块注释，说明：

- 该文件负责什么；
- 该文件不负责什么；
- 主要输入输出。

不得写冗长过程说明。

## 20.2 文件规模门禁

职责是第一拆分条件，行数和字节数是第二道硬门禁：

- 出现第二职责时，无论只有多少行，都必须立即升级为目录并拆分。
- TypeScript、JavaScript、CSS：目标不超过 250 行且不超过 12KB。
- Rust：目标不超过 300 行且不超过 16KB。
- 超过 300 行或 16KB：必须在当前 Atomic Task 内完成拆分审查。
- 超过 500 行或 24KB：默认硬性失败，不得合并；只有生成文件、历史迁移、保护区模型资产或机器可读静态数据允许例外。
- `main.ts`、`lib.rs`、`mod.rs`、`index.ts`、注册表和组合根目标不超过 150 行。
- 所有例外必须登记到 `architecture/file-size-exceptions.json`，包含原因、责任人、验证、到期条件和删除计划。

门禁不得促成按行数平均切割；拆分后的每个文件仍必须拥有可命名的单一职责和独立测试边界。

## 20.3 禁止文件名

禁止新建：

```text
utils.*
helpers.*
common.*
misc.*
manager.*
service.*   （除 application feature 的明确 service.rs）
new.*
old.*
legacy.*
copy.*
final.*
*v2.*
```

`service.rs` 只允许在应用服务边界中使用，且必须由目录名明确业务域。

## 20.4 Barrel 文件

`index.ts` / `mod.rs`：

- 只声明模块和导出。
- 不定义状态。
- 不执行副作用。
- 不写业务流程。

## 20.5 文件升级为目录的递归拆分规则

这是本次订正后的最高优先级模块化规则之一。

### 20.5.1 触发条件

只要现有文件出现以下任一情况，就必须把该文件代表的模块升级为同名目录：

- 需要增加第二个可独立命名的职责；
- 需要增加同模块的新视图、新状态、新控制器、新 API、新校验、新映射或新测试；
- 原文件已有内容需要进一步拆出，而新内容与其仍属于同一个上级模块；
- 文件虽然行数不大，但存在不同变更原因、不同状态所有者或不同副作用；
- 新想法会迫使原文件新增第二种业务动作。

### 20.5.2 正确迁移方式

假设原文件为：

```text
features/teams/directory/teamDirectory.ts
```

现在需要新增筛选、分页和选择能力，禁止继续写入该文件，也禁止在 `directory/` 根部随意平铺。必须升级为：

```text
features/teams/directory/team-directory/
├─ index.ts                         # 只导出本子模块公共入口
├─ teamDirectory.ts                 # 保留原文件的单一目录编排职责
├─ teamDirectoryView.ts             # 目录 DOM 输出
├─ teamDirectoryController.ts       # 目录事件和生命周期
├─ teamDirectoryState.ts            # 目录本地状态
├─ teamDirectorySelectors.ts        # 目录派生状态
├─ filters/
│  ├─ index.ts
│  ├─ teamFilters.ts
│  ├─ teamFilterView.ts
│  └─ teamFilterState.ts
├─ pagination/
│  ├─ index.ts
│  ├─ teamPager.ts
│  └─ teamPageCursor.ts
└─ selection/
   ├─ index.ts
   ├─ teamSelection.ts
   └─ teamSelectionState.ts
```

这里的“原文件”和“新文件”是职责概念，不允许最终命名为 `old.ts`、`new.ts`。原文件可以保留原文件名，但必须移动进模块目录，并继续保持唯一职责。

### 20.5.3 递归升级

如果后续 `teamFilters.ts` 又需要拆成条件编辑、已选条件展示和查询序列化，则再次升级：

```text
filters/team-filters/
├─ index.ts
├─ teamFilters.ts
├─ teamFilterEditor.ts
├─ selectedTeamFilters.ts
└─ teamFilterQueryMapper.ts
```

不得因为已经建立过一层目录，就把后续所有内容重新塞进其中某个文件。

### 20.5.4 后端同样执行

Rust、脚本、CSS、测试和契约文件同样适用：

```text
commands/prediction/run_prediction.rs
```

若该命令需要拆分输入 DTO、权限检查、映射和响应 DTO，则升级为：

```text
commands/prediction/run-prediction/
├─ mod.rs
├─ command.rs
├─ input.rs
├─ output.rs
├─ authorization.rs
└─ mapping.rs
```

```text
styles/features/teams.css
```

### 20.5.5 禁止的伪拆分

- 原文件保留全部逻辑，新文件只做转发；

- 把多个动作从 `client.ts` 搬到新的 `api.ts`；

- 以“同一页面”为理由把页面所有功能放入一个文件；

# 22. 新想法与未来功能的接入协议

任何未来新增想法都必须先完成模块归属，再进入编码；不得先把代码写进当前最接近的文件。

## 22.1 新需求进入前的八项定位

每个新想法必须明确：

1. 属于现有 feature、现有子模块，还是全新 feature；
2. 谁拥有它的业务状态；
3. 谁拥有它的副作用；
4. 是否新增公共契约；
5. 是否新增 Tauri 命令或 application use case；
6. 是否需要持久化、事务或迁移；
7. UI 中属于页面、区域、组件、弹窗还是工作流；
8. 需要哪些单元、契约、集成和 UI 回归测试。

其中任一项无法明确时，不得开始写代码。

## 22.2 新想法的目录决策树

```text
新想法
├─ 只改变现有单一职责内部实现
│  └─ 可修改原职责文件，但不得增加第二职责
├─ 为现有模块增加一个独立职责
│  └─ 按“文件升级为目录”规则创建子目录和新文件
├─ 为现有 feature 增加独立子功能
│  └─ 在 feature 下创建具名子模块目录
├─ 跨越两个 feature
│  ├─ 先判断是否是共享视觉原语
│  ├─ 先判断是否是应用级协调流程
│  └─ 禁止直接让两个 feature 共享可变状态
└─ 全新业务能力
   └─ 创建完整 feature + contract + use case + adapter + test 纵向切片
```

## 22.3 新 Feature 的最小完整纵向切片

```text
src/features/<feature>/
contracts/<feature>/
crates/domain/src/<feature>/                 # 仅存在真正领域概念时
crates/application/src/features/<feature>/
crates/application/src/ports/<feature>/      # 仅存在外部端口时
crates/persistence-postgres/src/<feature>/   # 仅需要数据库时
src-tauri/src/commands/<feature>/
tests/contracts/<feature>/
tests/frontend/features/<feature>/
tests/integration/<feature>/
architecture/modules/<feature>.json
```

不得只创建前端页面后把后端调用临时塞进其他 feature，也不得只创建数据库表而没有明确 application use case。

## 22.4 模块清单同步

新增、删除、拆分或合并模块时，必须同步修改：

- `architecture/modules/<module>.json`；
- `architecture/module-boundaries.json`；
- `architecture/command-contract.json`（涉及命令时）；
- 对应契约、测试与 README 实施记录；
- 受影响目录的 `README.md`（仅顶级复杂模块需要）。

## 22.5 未来扩展的禁止路径

- 在 `main.ts` 增加页面业务；
- 在全局 API 客户端增加新命令；
- 在全局 `types.ts` 增加新 DTO；
- 在现有页面 view 中直接调用 API；
- 在 Tauri 命令中写 SQL；
- 在 application service 根文件追加业务流程；
- 在通用 CSS 文件追加 feature 样式；
- 通过复制旧模块创建 `xxx2`、`xxx_new`、`xxx_final`；
- 创建没有退出期限的兼容层。

## 23.3 阶段与节点实施记录制度

### 23.3.1 目的与效力

从 R0 开始，每完成一个阶段或一个阶段内的 Atomic Task，必须在仓库根目录 `docs/` 下保存对应的详细实施记录。该记录属于交付物和阶段门禁，不是可选说明。

规则效力：

- 源码已经实现但没有节点记录：任务不得标记为 `DONE`。
- 节点全部完成但没有阶段总结：阶段不得通过出口门禁。
- 只有根 `README.md` 摘要而没有 `docs/` 详细记录：视为记录不完整。
- 只有计划、预期或模板，没有填写真实变更与真实验证结果：视为未记录。
- 记录与 `git diff`、测试结果或最终代码不一致：阶段必须停止并订正。

根 `README.md` 继续承担项目级摘要；`docs/modular-rewrite/` 承担节点级和阶段级完整事实记录。两者不能互相替代。

### 23.3.2 固定目录

```text

   ├─ R06-entity-catalog-persistence/

```

阶段目录使用固定编号和稳定语义名称，不得临时改成 `new`、`final`、`done`、日期或人员姓名。后续新增阶段时，必须延续同一编号规则。

每个阶段目录至少包含：


- `README.md`：当前阶段索引、任务状态、记录链接、阶段门禁状态。
- `<task-id>-<task-name>.md`：一个 Atomic Task 的完整实施事实。一个节点一个文件，不得把多个节点合并为流水账。
- `<stage-id>-stage-completion.md`：整个阶段完成后的汇总、阶段回归和进入下一阶段的依据。
- `evidence/`：保存需要长期保留且体积受控的验收证据，例如结构化报告、截图索引、迁移指纹摘要。不得提交构建产物、依赖缓存、数据库转储、密钥或巨量原始日志。

### 23.3.3 创建与更新时机

1. 阶段第一个任务进入 `READY` 前，创建阶段目录及其 `README.md`。
2. Atomic Task 进入 `IN_PROGRESS` 时，在阶段 `README.md` 中记录负责人、起始基线、影响范围和状态。
3. 完成代码、最小验证和阶段相关回归后，基于真实 `git diff` 创建该节点的详细记录。
4. 节点记录、根 `README.md` 摘要和阶段索引全部更新后，任务才可改为 `DONE`。
5. 阶段内所有节点完成并通过出口门禁后，创建 `<stage-id>-stage-completion.md`。
6. 阶段总结完成并与真实验证结果一致后，下一阶段第一个任务才可进入 `READY`。

- 验证记录必须写明真实命令、真实结果和执行环境，不得写“理论通过”“应当通过”。
- 任务完成记录创建后不得无痕覆盖。事实订正必须在原文件追加“订正记录”，说明订正原因、内容和对应提交。
- 不得复制上一节点记录后只改标题；每个节点必须反映真实差异。
- 不得把详细过程全部堆进根 README；根 README 只保留摘要并链接到阶段记录。
- 不得在记录中写入密码、Token、连接串、个人隐私或未脱敏日志。

### 23.3.8 完成硬门禁

Atomic Task 从 `VERIFYING` 进入 `DONE` 前必须同时满足：

1. 节点代码和测试已经完成。
2. 最小验证通过或受阻项已按规则完整记录。

4. 阶段 `README.md` 已更新任务状态和记录链接。
5. 根 `README.md` 已写入项目级摘要。
6. 文件清单与实际 `git diff` 一致。
7. 旧实现删除和入口切换结果已记录。
8. 回退点明确。

# 27. 最终验收标准

## 27.1 架构

- 每个业务能力有唯一目录。
- 每个文件有唯一职责。
- 依赖方向通过机器门禁。
- 无循环依赖。
- 无跨层直接调用。
- 无全局业务状态中心。
- 无巨型 API 中心。
- 无巨型类型中心。
- 无巨型业务组合根。

## 27.2 功能

- 所有现有页面可用。
- 所有现有命令可用。
- 所有现有数据可读取。
- 所有正式写入保持事务和审计。
- Excel、AI 包、复盘包兼容。
- 搜索、分页、状态恢复、异步取消正常。
- 运行日志完整且脱敏。

## 27.3 模型

- 保护资产 SHA-256 一致。
- P7 固定回归一致。
- P4 Golden Master 一致。
- P4/P7 输入输出 Schema 一致。
- P4.4 仍为 SHADOW_ONLY。
- 正式路由和时点一致。
- 快照和输入指纹语义一致。

## 27.4 质量

- TypeScript strict 通过。
- Vite build 通过。
- cargo fmt 通过。
- cargo clippy `-D warnings` 通过。
- cargo test workspace 通过。
- PostgreSQL integration 通过。
- UI screenshot 通过。
- Windows acceptance 通过或明确记录环境阻塞。
- 无被跳过或弱化的失败测试。

## 27.5 清理

- 无旧实现。
- 无重复实现。
- 无临时适配。
- 无调试代码。
- 无构建产物。
- 无未说明警告。
- README 与实际结果一致。
