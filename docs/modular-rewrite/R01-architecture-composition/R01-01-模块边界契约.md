## 2. 原始问题与节点目标

- 现有模块边界分散在 Cargo 清单、前端入口、Tauri 命令、应用服务和人工说明中，缺少机器可读的统一依赖契约。
- 浏览器、Application、Persistence、Tauri 和 Windows 凭据中的共享状态已有实际所有者，但没有统一、可验证的唯一所有权声明。
- 本节点建立模块依赖与状态所有权两份权威 JSON，为 R1-02 自动边界门禁和 R1-03 至 R1-05 组合根拆分提供固定输入。
- 本节点不迁移 Feature、Domain、Repository 或命令实现，不拆分业务入口，不改变公共接口、运行行为、配置、依赖、数据库、模型或 UI。

## 3. 实际实现

### 3.1 架构契约

- 新增 `architecture/module-boundaries.json`：登记 18 个前端 Feature、11 个 Rust workspace 成员、4 个应用端口、32 个 PostgreSQL 适配模块、15 个 Tauri 命令组，并继续以 `architecture/command-contract.json` 作为 171 个公共命令的唯一权威清单。
- 新增 `architecture/state-ownership.json`：登记 17 个共享状态的唯一当前所有者、读写边界、禁止所有者和计划迁移目标。
- R1-03、R1-04、R1-05 的目标位置仅作为计划迁移目标；对应 Atomic Task 完成前，当前所有权不变化。

### 3.2 GitHub Actions Windows 自动门禁

- 更新 `.github/workflows/ci.yml`，支持以下触发方式：
  - 推送到 `main`；
  - 推送到 `new-*`；
  - 推送到 `rewrite/**`；
  - Pull Request；
  - `workflow_dispatch` 手动触发。
- 主验证环境改为 `windows-latest`，与项目 Windows-only 交付边界一致。
- 工作流执行 R1 架构 JSON smoke check，并调用既有 `scripts/windows-acceptance.ps1 -Mode Automated`。
- 自动验收覆盖依赖安装、前端契约与构建、Rust 格式与严格 Clippy、workspace tests、Tauri Windows release 构建、release 客户端启动和运行日志扫描。
- 工作流在任何成功或失败状态下上传验收日志和可用的 release bundle 证据。
- 使用 concurrency 取消同一分支被新提交取代的旧运行，避免无意义的并行资源消耗。

### 3.3 Windows 换行兼容

- 新增 `.gitattributes`：普通文本固定为 LF，`.bat`/`.cmd` 保持 CRLF，图片、PDF、Excel、ZIP 等明确为二进制。
- 下列验证器统一在读取文本时把 CRLF/CR 规范为 LF，避免 Windows 棠出改变冻结合同字节后产生伪失败：
  - `scripts/verify-inline-workspace-and-resource-scroll.mjs`
  - `scripts/verify-api-workspace.mjs`
  - `scripts/verify-team-player-management.mjs`
  - `scripts/verify-team-package-import-normalization.mjs`
  - `scripts/verify-entity-relationships.mjs`
  - `scripts/verify-formation-usage.mjs`
  - `scripts/verify-monthly-workbooks.mjs`
  - `scripts/verify-match-lineup-chain.mjs`
- 合同哈希仍覆盖规范化后的完整合同文本；冻结合同、迁移文件及迁移内登记哈希均未更新或放宽。

### 3.4 State 生命周期专项门禁

- `scripts/verify-force-team-delete.mjs` 原先要求源码必须出现字面量 `drop(state)`，与 `clippy -D warnings` 的 `dropping_references` 规则冲突。
- 专项断言改为验证真实所有权边界：`spawn_blocking(move || ...)` 只捕获拥有所有权的 `service`，不得捕获 `State` 借用。
- `src-tauri/src/commands/catalog.rs` 在诊断过程中曾临时加入两处 `drop(state)`，随后按 Clippy 结果删除；最终生产源码保持 service clone 的既有写法，命令行为未变化。
- 没有增加 `allow`、关闭 Clippy、跳过专项验证或降低失败等级。

## 5. 边界与所有权决策

### 5.1 前端

- `src/main.ts` 仍是当前浏览器组合和页面编排所有者，只标记为 R1-03 的待迁移入口。
- `src/api/client.ts` 继续拥有 Tauri transport；页面和 `src/app` 不得直接导入 `@tauri-apps/api/core`。
- 18 个页面文件继续作为当前 Feature owner；`src/features/<feature>` 只是后续目标位置，本节点不创建复制实现。
- `src/app/viewState.ts`、`src/app/navigation.ts`、`src/app/modal.ts` 分别继续拥有工作区文档、导航竞态状态和详情历史。

### 5.2 Rust/Application/Persistence

- Cargo 清单中的现有 workspace 依赖作为允许边，不虚构不存在的依赖倒置层。
- `football-domain` 保持零 workspace 内部依赖。
- `PredictionModel`、`OpenAiTransport`、`GatewayAttemptSink`、`ApiKeyProvider` 作为现有端口登记。
- SQLx/PostgreSQL pool 只由 `football-persistence-postgres` 所有。
- `ApplicationService` 继续唯一持有 `ModelRegistry`、活动数据库与 P4 worker guard；R1-05 完成前不改变。

### 5.3 Tauri 与公共命令

- `src-tauri/src/lib.rs::run` 仍是桌面组合入口。
- `src-tauri/src/commands.rs::AppState` 仍是桌面共享引用容器。
- 171 个公共命令不在新契约中复制第二份名称清单；新契约只登记数量、注册所有者和 15 个命令组。
- 命令名称、参数、返回类型、注册顺序、启动行为和窗口行为均未改变。

## 6. 保持不变的行为
