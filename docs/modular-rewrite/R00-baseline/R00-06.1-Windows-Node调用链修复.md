## 2. 实际问题

R0-06 的 Windows 基线确认两个同源调用问题：

1. `scripts/ensure-node-dependencies.mjs` 用字符串路径相等判断是否直接执行。Windows 验收通过 `项目源码` 目录联接进入仓库时，`process.argv[1]` 与 `import.meta.url` 分别指向联接路径和物理路径，导致安装脚本未执行却返回零退出码。
2. `scripts/verify-frontend.mjs` 直接通过 `spawnSync` 启动 `node_modules/.bin/tsc.cmd` 和 `vite.cmd`。Windows Node 子进程接口对该调用返回 `EINVAL`。

结果是 Automated 依赖阶段可能假通过，前端阶段随后因缺少 `typescript` 或 `.cmd` 启动失败而中断。

## 3. 实际修改

### 新增模块

| 文件 | 唯一职责 |
|---|---|
| `scripts/process/execution-context.mjs` | 将执行入口与模块文件解析到规范物理路径，兼容 Windows 目录联接和大小写差异 |
| `scripts/process/node-package-cli.mjs` | 校验并解析本地 Node 包 CLI，统一使用当前 `process.execPath` 启动 JavaScript 入口 |
| `scripts/verify-node-process-compatibility.mjs` | 验证联接路径、CLI 参数传递、成功退出、非零退出码和缺失入口拒绝行为 |

### 修改模块

| 文件 | 修改内容 |
|---|---|
| `scripts/ensure-node-dependencies.mjs` | 使用规范路径判断直接执行；Windows 无 `npm_execpath` 时通过 `ComSpec /d /s /c npm.cmd` 执行 npm |
| `scripts/verify-frontend.mjs` | 将 TypeScript 与 Vite 改为通过 Node 执行各自真实 JavaScript CLI；接入专项兼容验证 |
| `scripts/verify-windows-acceptance.mjs` | 将已经过时的 README 精确文本断言改为同等强度的语义存在性检查，避免文档换行造成假失败 |

临时 `.github/workflows/r00-windows-node-compat.yml` 仅用于本节点 Windows 取证，验证完成后已删除。

## 4. 模块边界

调用链变为：

```text
verify-frontend.mjs
  ├─ Node 验证脚本：process.execPath + 脚本绝对路径
  ├─ TypeScript：process.execPath + node_modules/typescript/bin/tsc
  └─ Vite：process.execPath + node_modules/vite/bin/vite.js
```

`execution-context.mjs` 只负责执行身份判断；`node-package-cli.mjs` 只负责本地 CLI 解析与执行；前端总验证器只负责排序和失败传播。

## 5. 保持不变的行为
